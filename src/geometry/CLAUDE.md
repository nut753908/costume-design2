# src/geometry/ のガイダンス

全体のアーキテクチャ概要(手続き的生成・外部アセット不使用という制約を含む)は[ルートの CLAUDE.md](../../CLAUDE.md)を参照してください。

## カスタムガーメントジオメトリ

ガーメントは全14種類(skirt/top(袖込み)/pants/shoes/gloves/hat/belt/scarf/jacket/socks/dress/bag/necktie/glasses)あり、scarf/shoes/bag/glasses を除く11種は `build*Geometry(params) -> THREE.BufferGeometry` という純粋関数として実装されています。scarf/shoes/bag/glasses は専用の `build*Geometry()` を持たず、既存の汎用ノードの組み合わせだけで完全にノードグラフ上に表現されている — scarf は `beltGenerator`/`boxGenerator`/`translate`/`mergeGeometry`(`nodes/definitions/groups/scarfGroupNode.ts` 参照、下記 belt の項も参照)、shoes は `easedLatheProfile`/`latheGenerator`/`scaleZ`/`mirrorPair`(`nodes/definitions/groups/shoesGroupNode.ts` 参照、下記参照)、bag/glasses は `boxGenerator`/`torusGenerator`/`alignedBoxGenerator`/`translate`/`translateZ`/`mirrorPair`/`mergeGeometry`(`nodes/definitions/groups/bagGroupNode.ts`/`glassesGroupNode.ts` 参照、下記参照)。共有ヘルパー:

- `latheProfile.ts` — `buildEasedLatheProfile()`。アンカー側から反対側の端まで、半径を smoothstep でイージングしながら結ぶプロファイル点列を生成する。大半のガーメント(skirt/pants/shoes/gloves/hat/belt/jacket/socks など)はこれを `THREE.LatheGeometry` に渡すだけの単純な回転体。skirt/pants(脚)/shoes/gloves/hat/jacket/socks の7種は、この関数呼び出し自体もノードグラフ側の汎用ノード `easedLatheProfile`(`nodes/definitions/generic/easedLatheProfile.ts`)+`latheGenerator`(`nodes/definitions/generic/latheGenerator.ts`、生の `THREE.LatheGeometry` ラッパー)へ切り出されており、対応する `<name>GroupNode.ts` から直接呼ばれる(下記参照)。この2ノードの間を流れる値(`THREE.Vector2[]` の点列)には `nodes/types.ts` の `SocketType`/`SocketValue` に `'points'` という専用の型がある(`nodes/CLAUDE.md` 参照)。`easedLatheProfile` の `direction`(`'up'`/`'down'`)/`steps`(プロファイルの分割数、既定10、skirt のみ12)は、`capsuleGenerator` の `capSegments`/`radialSegments` と同じくソケット化せず、ノード配置時の `data` に固定している — ガーメントごとに変える理由に乏しいスタイル寄りの値のため。skirt/jacket の裾半径(`hemRadius = radius * (1 + Math.max(0, flare))`)は `numberMax`(`numberAdd`/`numberSubtract`/`numberMultiply` と対になる二項演算ノード、`nodes/definitions/generic/numberMax.ts`)→`numberAdd`→`numberMultiply` という可視の配線へ展開してから `profile.endRadius` へ渡している(`skirtGroupNode.ts`/`jacketGroupNode.ts` の `zeroIn`/`oneIn` は `nodes/definitions/constNumberInput.ts` の `constNumberInput()` で定義する「常に一定の値を持つ `numberInput`」)。belt(プロファイルを2回呼んで連結する)は `easedLatheProfile`(`lowerProfile`/`upperProfile`)+`translatePointsY`(points を Y方向にだけ平行移動する、`translateY` の points 版)/`slicePoints`(points の末尾から指定個数を取り除く)/`concatPoints`(2つの points を連結する、`mergeGeometry` の points 版)へ展開し、`beltGroupNode.ts` から直接呼ばれる。shoes はつま先方向に伸びた楕円形のシルエットを作る非一様スケール(`.scale(1, 1, toeLength)`)も `scaleZ`(`translateX`/`translateY`/`translateZ` と対になる、1軸だけを扱う汎用の非一様スケールノード、`nodes/definitions/generic/scaleZ.ts`)へ展開している。
- 左右対称なパーツ(Body の腕/脚1組、pants の左右2脚、shoes の左右2本、gloves の左右2つ、socks の左右2本)の「±offset だけ平行移動して結合する」処理は、`geometry/` 側の専用関数としては存在しない。ノードグラフ上の `translateX`(`translateX.ts`)×2+`mergeGeometry`(`mergeGeometry.ts`、`mergeGeometries()`+`computeVertexNormals()` を切り出した汎用ノード)を内包するグループノード `mirrorPair`(`nodes/definitions/generic/mirrorPair.ts`)へ全ガーメント分統一されている。各ガーメントの `geometry/*.ts` はこの切り出しにより「1つぶんの形状を作る関数(`buildPantsLegGeometry()`/`buildGloveGeometry()`/`buildSockGeometry()`)」だけを持ち、左右対称ペア化のロジックは持たない(shoes は `geometry/shoes.ts` 自体が無く、プロファイル生成+Lathe化+非一様スケールもすべてノードグラフ側にある、上記参照)。
- `neckline.ts` — `necklineWeight()`。角度ごとのネックライン落ち込み量(round/v/square)を計算する、`ringGrid.ts` が使うフォールオフ関数。
- `ringGrid.ts` — `buildRingGridGeometry()`。角度×高さのリングからなる手組みの `BufferGeometry` を、行ごとの半径/Y座標のリストから組み立て、最上段のリングの頂点のみを角度ごとに(`neckline.ts` のフォールオフ関数で重み付けして)引き下げてネックラインを彫り込む。`top.ts`/`dress.ts` が共有する。
- `alignedBox.ts` — `buildAlignedBox()`。2点間を結ぶよう回転+平行移動した `THREE.BoxGeometry` を作る。回転+平行移動のみの剛体変換なので、標準プリミティブが元々持つ正しい巻き順がそのまま保たれる。`nodes/definitions/generic/alignedBoxGenerator.ts` がノードグラフへ薄く配線する(始点・終点をそれぞれ X/Y/Z の3ソケットに分解しているのは、座標を求める四則演算チェーンを可視の配線として展開できるようにするため。`points` 型を扱う `latheGenerator.ts` と同じ理由で `defineGeneratorNode()` ではなく直接 `registerNodeType()` で定義している)。bag のストラップ・glasses のブリッジ/テンプルが使う。
- `primitives.ts` — `buildCapsuleGeometry()`/`buildSphereGeometry()`/`buildCylinderGeometry()`/`buildTorusGeometry()`/`buildBoxGeometry()` という、THREE.js 標準プリミティブ(CapsuleGeometry/SphereGeometry/CylinderGeometry/TorusGeometry/BoxGeometry)をそのまま返すだけの、特定のガーメント/パーツに紐付かない汎用ジオメトリ関数群。`nodes/definitions/generic/capsuleGenerator.ts`/`sphereGenerator.ts`/`cylinderGenerator.ts`/`torusGenerator.ts`/`boxGenerator.ts` がノードグラフへ薄く配線する。`bodyGroupNode.ts` が Capsule/Sphere を胴体/頭に、Cylinder(`limbPair.ts` 経由)を腕/脚として使い、`mergeGeometry` で1つに結合してから単一の `sceneOutput` へ渡す(`nodes/CLAUDE.md` の「グループノード」節参照)。腕/脚1組は `cylinderGenerator` の出力を汎用グループノード `mirrorPair`(上記参照)へ渡して左右対称ペアにまとめる。bag/glasses は、単純な `.translate(x,y,z)` だけで配置できるパーツ(bag のバッグ本体、glasses の左右レンズ)と `alignedBoxGenerator`(2点間に整列させる回転+平行移動)を使うパーツ(bag のストラップ、glasses のブリッジ/テンプル)の両方を持つガーメントで、前者は `boxGenerator`/`torusGenerator`(プリミティブ生成)→`translate`(bag は X/Y/Z、glasses は Z のみの `translateZ`)、後者は `alignedBoxGenerator` というノードグラフへそれぞれ切り出し、`mergeGeometry` で結合している(どちらも専用の `build*Geometry()` は持たない)。

放射対称な Lathe では表現できない形状は、それぞれ別の技術で構築しています:

- `top.ts`/`dress.ts` — Lathe/Extrude では**ない**。ネックラインの落ち込みは放射対称ではないため。どちらも `ringGrid.ts` の `buildRingGridGeometry()` に「行ごとの半径/Y座標」のリストを渡すだけで、リング構築・インデックス組み立て・法線計算はそちらに任せている。`top.ts` は全行が torsoRadius で一定の半径リストを渡すだけ、`dress.ts` は `latheProfile.ts` のイージング済み半径プロファイルから半径リストを作ることで、肩(torsoRadius)から裾(hemRadius)まで半径が変化する1続きの形状にしている。
- `sleeve.ts` — 肩の各角度ごとにローカルな(外向き、接線、従法線)フレーム内で構築された、テーパー状の短い2本のチューブで、トルソーの壁面に食い込ませて重ねたままにしています(`bodyLayoutGroupNode.ts` の `armTorsoOverlapRatioIn` が腕に対して使っているのと同じ、意図的な交差を許容するアプローチで、ブーリアン演算や穴あけは行いません)。`topGroup` の内部で `topGenerator` と並べて使われ、Top と同じ(Body Build 適用後の)胴体半径を付け根半径として受け取り、結合後の1つのジオメトリとして同じ `toonMaterial`・同じ `shoulder` アンカーで描画される。これにより top の色を変えると sleeve も一緒に再着色される(`nodes/definitions/groups/topGroupNode.ts` 参照)。
- `necktie.ts` — sleeve.ts と同じ「行=長さ方向、列=断面の周」という手組みチューブの考え方を、円形断面ではなく矩形の4隅に置き換えたもの。
- マネキンの寸法計算(`heightScale`/`buildScale`/`shoulderScale` から各部位の半径・長さ・Y座標、および `waist`/`shoulder`/`feet`/`wrist`/`head` アンカー座標を求める式)は、`geometry/` 配下の純粋関数としては存在しません。式の実体は `bodyDimensionsGroupNode.ts`/`bodyLayoutGroupNode.ts` というノードグラフのテンプレート定義そのものが唯一の真実の源です(コード側に並行する純粋関数は無い、ノードエディタ上で式がそのまま見える形にするため)。`bodyDimensionsGroup`/`bodyLayoutGroup` 自体は `bodyGroupNode.ts`/`garmentPlacement.ts` のどちらにもネストされておらず、`src/state/initialGraph.ts` 側のトップレベル共有ノード(id: `bodyDimensions`/`bodyLayout`)としてただ1組だけ存在し、`bodyGroup` と全14ガーメントへ計算済みの値をファンアウトする(`nodes/CLAUDE.md` の「グループノード」節参照)。ボディのリサイズに合わせてアンカーが一緒に動きます。

- bag のストラップは `bagGroupNode.ts` 側で `alignedBoxGenerator`(始点 `(shoulderOffset, 0, strapStartDepthIn)` → 終点 `(negatedHipOffset, negatedDrop, bagFrontDepthIn)`)として組み立てる。バッグ本体は `boxGenerator`(width/height/depth)→`bodyTranslate`(`translate` グループ、`x = negatedHipOffset = 0 - hipOffset × bodyBuild`、`y = bagCenterY = (0 - drop) - bagHeight × 0.5`、`z = bagFrontDepthIn = 0.18 × bodyBuild`)というノードグラフで組み立て(体の側面の位置と前面の深さは胴体の壁と同様に Body Build でスケールする)、最後に `mergeGeometry` でストラップと結合する — ストラップの終点とバッグ本体は `negatedHipOffset`/`negatedDrop`/`bagFrontDepthIn` の計算結果を共有する。
- glasses は `glassesGroupNode.ts` 側で、ブリッジ・テンプルを `alignedBoxGenerator`、レンズを `torusGenerator` として組み立てる。ブリッジは1本の箱で、`bridgeXOffset = lensSpacing - lensRadius` の ± を両端の X に、Y=0・Z=`forwardDepthIn` は両端で共通。テンプルは X=0 に1本だけ作り(前面 `forwardDepthIn` から後方 `templeBackZ = (forwardDepthIn - templeBackOffsetIn) - templeLength` まで Z 方向に伸ばす)、`mirrorPair` で `templeXOffset = lensSpacing + lensRadius` の ± へ複製する。ブリッジ・テンプルペア・レンズペアは1つの `mergeGeometry` で結合する。レンズも1つだけ `torusGenerator`(radius=lensRadius、tube=frameThicknessの半分)→`translateZ`(`forwardDepthIn` = 頭半径 × `forwardDepthRatioIn`(0.875)、既定で 0.14)で作り、`mirrorPair` で `lensSpacing` の ± へ複製する。
- scarf は `geometry/scarf.ts` 自体が存在しない。首元の輪(帯)は既存の `beltGenerator` ノード(`buildBeltGeometry()` をそのまま呼ぶ)を `bulge=1.05` 固定で `scarfGroupNode.ts` にネストして再利用し、タイは `boxGenerator`→`translate`(Y: `(0-bandThickness) - tailLength×0.5`、Z: `neckRadius(スケール後) × 0.9` という可視の四則演算チェーンで導出)へ展開して `mergeGeometry` で結合している。scarf が首元の輪にこの `beltGenerator` を「値を1回呼ぶだけの部品」として再利用しているため、`geometry/belt.ts`/`nodes/definitions/groups/beltGenerator.ts` は belt グループ自身がノードグラフへ完全展開されていても呼び出し元があり、ファイルごと削除はしていない。

**すでに一度踏んだ落とし穴(新しいジオメトリを追加すると再びハマります):**

- 三角形の巻き順(winding order)は重要で、逆になりやすいです。しかも視覚的な症状は分かりやすい「裏返って見える」ではなく、ガーメントが**真っ黒なシルエット**としてレンダリングされる(端に本来の色がわずかに見えることもある)というものです。これは、実際の `FrontSide` メッシュが(誤って)カリングされると、アウトラインメッシュの `BackSide` 専用の面だけが唯一の可視面になってしまうために起きます。新しい手続き型メッシュが真っ黒にレンダリングされたら、まずマテリアルやライティングではなく三角形の巻き順を確認してください。`windingTestHelpers.ts` の `expectOutwardWinding()` で自動検証できますが、対象が単純な放射対称形状でない場合は既定の axisPoint(Y軸基準)では誤検知します — 箱(BoxGeometry)には自身の中心点、トーラス(TorusGeometry)には中心線円上の最近点というように、形状に応じた正しい基準点を渡す必要があります(`alignedBox.test.ts` 参照)。
- `mergeGeometries()`(`three/examples/jsm/utils/BufferGeometryUtils.js`)は、結合するすべてのジオメトリが**同じ頂点属性**(名前・itemSize)を持っていることを要求します。標準プリミティブ(position/normal/uv を持つ)と手組みの `BufferGeometry`(position のみ)を混ぜて結合しようとすると、警告を出して `null` を返し、その後の呼び出しが `Cannot read properties of null` で落ちます(`necktie.ts` で遭遇 — 手組み側にダミーの `uv` 属性を追加して解消)。
- アンカーは体の中心線(x=0, z=0)上の1点のみです。体の前面より前に出すべきアクセサリ(ネクタイ、バッグ、メガネなど)は、z=0 付近に置くとガーメントの壁の内側/裏側に埋もれて見えなくなります(`necktieGroupNode.ts` の `frontDepthIn`(Body Build でスケール)、`bagGroupNode.ts` の `bagFrontDepthIn`(0.18 × Body Build)/`glassesGroupNode.ts` の `forwardDepthIn`(頭半径 × 比率)を参照)。さらに、デフォルトグラフのように複数のガーメントが同じアンカーを同時に共有していると、後から広がる大きなガーメント(dress/jacket など)が薄いアクセサリ(necktie/bag など)を覆い隠すことがあります — これはバグではなく、複数の出力ノードが同じアンカーを共有する際の一般的な特性です(`src/scene/CLAUDE.md` の「シーン組み立て」参照)。
