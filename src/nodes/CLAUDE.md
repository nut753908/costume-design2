# src/nodes/ のガイダンス

全体のアーキテクチャ概要は[ルートの CLAUDE.md](../../CLAUDE.md)を参照してください。

## ノードグラフエンジン

React Flow (`src/editor/`) は UI の状態(ノードの位置、選択、ドラッグ)のみを保持します。実際の計算は、React Flow について何も知らない別の純粋関数レイヤーが担当します。

- `nodes/types.ts` — ソケットの型システム(`SocketType`: number/color/geometry/material/curve。入力ソケットの `SocketDef.multiple` が true なら複数のエッジを接続でき、`evaluate()` にはエッジの並び順で集めた値が `{ type: 'geometries' }` として渡される — 現在は `mergeGeometry` の `geometries` だけが使う)と `NodeTypeDefinition`(`inputs`/`outputs` ソケットと `evaluate(inputs, data) -> outputs` 関数を宣言)。`GraphNode`/`GraphEdge` もここで定義されており、React Flow 自身の `Node`/`Edge` 型から切り離された最小限の形になっているため、evaluator は UI ライブラリなしでも利用・テスト可能です。`curve`(`THREE.Curve<THREE.Vector2>`)は `easedLatheCurve`(`nodes/definitions/generic/easedLatheCurve.ts`、Lathe用のプロファイル曲線を生成)→`latheGenerator`(`nodes/definitions/generic/latheGenerator.ts`、曲線を分割した点列から生の `THREE.LatheGeometry` を作る)という生成〜消費の間を流れる値のための型で、geometry/material と同じくリテラルなデフォルトを表現できません(`groupIOSocket.ts` の `literalGroupInputValue()` 参照)。`translateCurveY`/`concatCurve`(`nodes/definitions/generic/`)は、`bulgedBand`(`generic/bulgedBand.ts`)が2つの `easedLatheCurve` の結果を連結する際に使う、curve を直接操作する汎用ノード。色は `editor/socketColors.ts` の `SOCKET_COLORS` に追加してあります。
- **未接続ソケットのリテラル値(`SocketDef.default`)**: `number`/`color` の入力ソケットは `default`(number は数値、color は hex 文字列)を宣言でき、宣言があるソケットはノードカード上で未接続のときに入力欄(`editor/nodeComponents/SocketField.tsx`)が出る。値は `data[socket.id]` に保持され、`evaluateGraph()` が未接続の入力として `evaluate()` へ渡す。`geometry`/`material`/`curve` はリテラルを持てないので `default` を持たない。グループノードのソケットの `default` は内部の `groupInput` の `data.sockets` から転送される(`resolveNodeSockets()`)。新しいノードタイプの `number`/`color` 入力には `default` を付けること(`defineGeneratorNode()` は `fields` の `default` を自動で付ける)。複数のノードで値を共有したい場合や、グループ内で調整したい共有パラメータは、`numberInput`/`colorInput` を配線する。
- `nodes/evaluateGraph.ts` — evaluator 本体。ノードをトポロジカルソートし(Kahn のアルゴリズム、循環がある場合は `GraphCycleError` を投げる)、順番に各ノードの `evaluate()` を評価します。**未接続の入力ソケットは、そのノード自身のリテラルな `data[socketId]`(無ければ `SocketDef.default`)の値にフォールバックします** — これは Geometry Nodes で未接続のソケットがウィジェットのデフォルト値を使うのと同じ挙動であり、単独の(未接続の)ノードでも動作するようにするための中心的な仕組みです。この未接続ソケットの解決ループは `nodes/resolveNodeSockets.ts` の `resolveNodeSockets(type, data)` を経由します(型の静的な `inputs` ではなく、グループノードインスタンス内部の `groupInput`/`groupOutput` ノードの `data.sockets` があればそちらを優先する — グループノードの動的ソケット用、下記「グループノード」節参照)。

  **ノード単位のメモ化キャッシュ**: `evaluateGraph()` はモジュールレベルの `WeakMap`(キーは各ノードの `node.data` オブジェクトそのもの)で、直前に評価したときの解決済み `inputs` と結果を覚えている。ある呼び出しで、あるノードの `node.data` 参照が前回と同じ(= 編集されていない)、かつ解決済み `inputs` も前回と値が同じであれば、`def.evaluate()` を呼ばずに前回の結果オブジェクトをそのまま返す。`number`/`color` は値そのもので比較し、`geometry`/`material`/`curve` は参照比較のみ(構造の深い比較は再計算とコストが変わらないため)——生成元のノードもキャッシュヒットして同じ参照を返している限り、この参照比較は連鎖的に成立する。`state/graphStore.ts` の全アクションはイミュータブルな更新しか行わず、変化していないノードは常に同じ `data` 参照を保つ(`src/state/CLAUDE.md` 参照)ため、これが「このノードは編集されていないか」の安価な判定として機能する。`evaluateGraph()` は最上位の呼び出し(`state/useRootEvaluatedGraph.ts` 等)からグループノードの埋め込みサブグラフの中(`groupNodeFactory.ts` の `evaluate()` が呼ぶ再帰呼び出し)まで同じ実装を共有しているため、このキャッシュも階層を問わず一様に効く——トップレベルで1つのスライダーを動かしても、それに依存しない他のグループは `groupNodeFactory.ts` の `evaluate()` 自体(＝内部サブグラフのフル評価)がまるごとスキップされる。`WeakMap` にしているため、ノードが削除されて `data` オブジェクトがどこからも参照されなくなれば対応するキャッシュエントリも GC に任せて自動的に回収され、手動の無効化ロジックは不要。キャッシュのヒット/ミスの累計は `getNodeEvalCacheStats()` で読め、`App.tsx` の右下の `evaluations` カウンターの隣に表示している(グループ内部の再帰評価分も含む累計で、例えば無関係なスライダーを動かしたときにミスが増えず、ヒットだけが増えることで効いているかを確認できる)。
  - **`data` のミューテートへの備え**: キャッシュエントリは登録時点の `node.data` のトップレベルの浅いスナップショットも持ち、ヒット判定で現在の `data` と比較する。参照が同じでも誰かが `data` のトップレベルのフィールドを直接書き換えていればヒットさせず再評価する(このアプリの更新経路は常にイミュータブルなので通常は起きない)。ネストしたオブジェクト(グループノードの `data.nodes` の中身など)の直接ミューテートまでは検知しないため、更新は必ず新しいオブジェクトを作って差し替えること。
- **このキャッシュが正しく働くための前提**: 各ノードタイプの `evaluate(inputs, data)` は `inputs`/`data` だけに依存する純粋関数であり続けること(隠れたグローバル状態を読まない)、そして `inputs` として受け取った `geometry`/`material`/`curve` を(`.clone()` 等せずに)直接ミューテートしないこと。既存の全ノード実装は最初からこの前提を満たしている(`translate.ts`/`scale.ts` が入力ジオメトリを `.clone()` してから変換するのがその一例)が、新しいノードタイプを追加する際もこの2点を破らないこと——破ると、キャッシュが返す「前回の結果への参照」が呼び出し元の意図しない形で書き換わり、無関係な箇所に伝播しうる。
  - **テストへの影響**: `getNodeType(type).evaluate(...)` を同じ型・同じ inputs で複数回呼ぶテスト(特に内部で `build*Geometry()` を spy する `topGroupNode.test.ts`/`dressGroupNode.test.ts`/`necktieGroupNode.test.ts` のようなテスト)は、キャッシュヒットにより2回目以降 `evaluate()` 自体が呼ばれず spy が発火しないことがある。`src/testSetup.ts` が全テストの `beforeEach` で `resetNodeEvalCacheForTests()`(`evaluateGraph.ts` がテスト専用に export)を呼び、キャッシュを毎回空にしてテストどうしを独立させている。
- 出力カテゴリのノードのうち `sceneOutput`(`nodes/definitions/generic/sceneOutput.ts`)は、描画専用の終端ノードで、`Garments.tsx` が `rootEvaluatedResults` から直接読み取る。**必ず `<name>Group` の埋め込みサブグラフの中に置く**(転送の仕組みは下記「グループノード」節の `sceneOutput` の項目、`src/scene/CLAUDE.md` 参照)。「型が geometry+material を持っていれば自動描画される」という暗黙の検出ではなく、「明示的に `sceneOutput` へ配線されているか」が描画対象かどうかの仕様そのもの — `groupOutput` 経由の通常出力は、どんな値があっても描画対象にならない。

## 新しいノードタイプの追加

手順は `add-node-type` スキルを参照してください。

`defineGroupNode()` のテンプレートで存在しないノード id/ソケット id を指すエッジを書いても、`evaluateGraph` は静かに無視して評価を続けるため実行時には気づけない。`nodes/definitions/groupNodeWiring.test.ts` が登録済みの全グループ型について、内部ノードの type が登録済みであること・内部エッジの端点が実在するノードの実在するソケットを指すこと・1入力に複数エッジが接続されていないことを走査して検証するので、グループを追加/配線し直したらこのテストで確認できる。

## グループノード

`nodes/definitions/groupNodeFactory.ts` の `defineGroupNode()` は、複数の既存ノード(`numberMultiply`+generator+`toonMaterial`+`garmentPlacement` など)を1つの埋め込みサブグラフとして内包し、外部には限られた入出力ソケットだけを見せる「グループノード」を定義する。`category: 'group'` 固定(`NodeCategory` に追加済み、パレットでは、ガーメントと Body 関連(`paletteSection: 'garment'`)は「Garments & Body」、自作グループ(`paletteSection: 'group'`)は「Group」、それ以外の部品・補助は「Group Parts」に表示される)。`src/state/initialGraph.ts` の全14種のガーメント(`<name>GroupNode.ts`、例: `skirtGroupNode.ts`)がこのパターンで定義されている(top は袖(`sleevePair`)も内包し、Top 本体と袖を `mergeGeometry` で結合して1つの `sceneOutput` へ渡す)。Body(3Dモデル本体)も `bodyGroup`(`bodyGroupNode.ts`)として同じパターンに乗っており、ガーメント/Bodyを合わせて `src/state/initialGraph.ts` 直下には計15個の `<name>Group` ノードが存在する — ただし `bodyGroup` は `garmentPlacement`(下記参照)を使わない点が他のガーメントと異なる(Body には取り付けアンカーの概念が無く、`bodyLayout` が計算した Center Y をそのまま `translateY` へ渡すだけで済むため)。

`bodyGroup` は胴体と首を1本の連続した輪郭(`torsoShape`、`generic/torsoShape.ts` — 幅(X)・前後の厚み(Z)の `profileCurve33` と、輪を前後へずらす `signedProfileCurve33` から `loftGenerator` で断面が楕円の胴体を作るグループノード。首は胴体の延長で、入力欄 `extra` に首の長さの 2.4 倍を渡す。胴体より前へ傾く首の曲がりは輪のずらしで表す)として作り、股(原点)を支点に `rotate` で前後へ傾け(入力欄 `x`、負なら上端が後ろへ倒れる)・頭(`headShape`、`generic/headShape.ts`、同じ構成。耳は `earPair` が左右の小さな楕円体で作る。肌は影の色つき)を `translate`(Y だけを配線して平行移動する汎用ノード。頭は入力欄 `z` で後ろへずらす)で配置し、腕1組/脚1組(`limbPair`、`nodes/definitions/generic/limbPair.ts` — 軸(`armShaft`/`legShaft`、`generic/limbShaft.ts`、同じ構成で付け根と先端の球の外側まで伸びる)を外部入力で受け取り、先端に手の球(`limbEnd`、`generic/limbEnd.ts`。`end` 入力で受け取る)を付け(足は `footShape`(`generic/footShape.ts` — 幅・厚み・足裏側へのずらしの3本の曲線から作る)を `foot` 入力で受け取り、先端の高さに置く。脚の `limbEnd` は半径を小さくして足に隠す)(根元の丸みは軸が閉じるので関節の球は付けない — 継ぎ目の輪になる)、根元(軸の上端の丸みの中心)を支点に `rotate`(汎用の回転ノード、度数)で先端を外へ `swingAngle` 度・後ろへ `pitchAngle` 度振り、左右ペア全体を `centerZ` で前後へずらし、`mirrorPair` で左右対称ペアにして `translate` で配置するグループノード。手/足の形は `bodyGroup` 側の入力欄の値)とあわせて1つの `mergeGeometry` で結合し、`sceneOutput` 1個だけへ配線している。腕と脚の太さの変化(太ももなど)は、`armShaft`/`legShaft` の3枚の `profileCurve` カードに別々の値を持たせる。脚の軸は `legShaftAdjust`の `trim` だけ下端を短くして足の後ろ下から軸の下端の角がはみ出さないようにし、`raise` だけ上端を胴体の下端へ食い込むまで伸ばす(下端は動かさない)。胴体も `torsoLift`(`numberInput`)だけ下端を持ち上げて股下を合わせ(上端は動かさない)、減った腰まわりは脚の軸の上端で補う。腕の付け根は `armShaftAdjust` の `drop` だけ下げて胴体の中へ埋め(肩の上に球が盛り上がらないように。手の位置は変えないよう、長さを `drop` 短く・中心を半分下げて `armPair` へ渡す)、`inset` だけ首側へ寄せる。全パーツが同じマテリアルなので、結合した方がグラフの階層が浅くなる。
**単独のノードだけが使う値(テーパー比率、固定の深さ、0/1/-1 のような定数など)は、`numberInput`/`colorInput` ノードを置かず、そのノードの入力欄の値(`data[socketId]`)としてテンプレートに書く**(`numberMultiply` の `factor` に `{ factor: 0.85 }` を書く、など)— 入力欄はノードカード上に表示されるので値は隠れず、ノード・エッジの数も減る(上記「未接続ソケットのリテラル値」参照)。**複数のノードが同じ値を使う場合は、`numberInput`/`colorInput` ノードを1つ置いて配線する**(`bagGroupNode.ts` の `bagHeightIn`、`glassesGroupNode.ts` の `lensRadiusIn` など)。`groupOutput` の `number`/`color` の入力も、何も配線されていなければ入力欄(`socket.default`)の値を出力するので、定数を出力へ渡す場合は `numberInput` を置かず、そのソケットの入力欄の値に持たせる(`bodyDimensionsGroupNode.ts` の `headRadius`)。

`bodyDimensionsGroup`(`bodyDimensionsGroupNode.ts`)/`bodyLayoutGroup`(`bodyLayoutGroupNode.ts`)という2つの `<name>Group` 型は、ボディの各部位の半径・長さ(11出力)と配置Y座標(7出力、うち `waistY`/`shoulderY`/`feetY`/`wristY`/`headCenterY` の5つはガーメントの取り付けアンカー候補を兼ねる)を計算する。各部位の計算は `numberMultiply`(基準値は `Value` 入力欄、Height/Build/Shoulder のスケールを `Factor` に掛ける)の形で、`bodyDimensionsGroup` はこれを11個の部位パラメータぶん内部に持つ。Height/Build/Shoulder のスケールは `bodyDimensions` からしか参照されないため、ルートで配線せず外部ソケット `heightScale`/`buildScale`/`shoulderScale`(未接続時の既定値1)としてグループカードの入力欄から調整する。胴体/首/頭/腕/脚のY座標配置も `numberAdd`/`numberSubtract`/`numberMultiply` の四則演算チェーンとして `bodyLayoutGroup` の内部に持つ。地面の高さ `feetY`(外部ソケット、既定値 0)は `waistY`/`legCenterY` に加算され、そこから積み上がる胴体/頭/腕の Y 座標もすべて連動するため、`feetY` を変えると体全体が上下する。いずれもブラックボックスの計算ノードではなく、「→」ボタンで中に入れば実際の式がそのまま見える。
この2つは `bodyGroup` の専用物でも `garmentPlacement` の専用物でもなく、`src/state/initialGraph.ts` 側のトップレベル共有ノード(id: `bodyDimensions`/`bodyLayout`)としてただ1組だけ存在し、`bodyGroup` と全14ガーメントへ普通の外部ソケットとしてファンアウトされている(「値が複数グループで共有される場合はトップレベルの共有ノードへ引き上げる」パターン、下記「値が複数グループで共有される場合」節参照)。ルートキャンバス上には "Body Dimensions"/"Body Layout" という独立した2枚のカードが直接見え、「→」ボタンを押せばその中の実際の四則演算グラフが見える。

- **外部インターフェースは Blender の Geometry Nodes と同じく「Group Input」「Group Output」ノードそのものが定義する**。`nodes/definitions/groupInput.ts`/`groupOutput.ts`(`category: 'group-io'`、パレットでは自作グループと同じ「Group」セクション — グループの中に入っている間だけ表示される、下記編集UX参照)がこれらのノードタイプで、`data.sockets: GroupIOSocket[]`(`nodes/definitions/groupIOSocket.ts`)という動的なソケット一覧を持つ。`groupInput` は `data.sockets` がそのまま動的な**出力**ソケット一覧に、`groupOutput` は動的な**入力**ソケット一覧になる(`nodes/resolveNodeSockets.ts` がこの2つの型名を特別扱いする)。グループノード本体(`category:'group'`)が外部に見せる入出力ソケットは、埋め込みサブグラフ内にあるこの2ノードの `data.sockets` からそのまま転送される(`resolveNodeSockets()` が `data.nodes` の中から `type: 'groupInput'`/`'groupOutput'` のノードを探して転送する)。**中に入って、この2ノードにソケットを増減・配線するだけで、グループ本体の外部から見えるハンドルが増減する**。Blender と同じく、同じ階層に `groupInput`/`groupOutput` を複数置ける。同じ型のノードは `data.sockets` を共有し(`state/groupIOSockets.ts` の `shareGroupIOSockets()` を、`updateNodeData`/`addNode`/貼り付け/`removeGroupIOSocket` が通す)、外部から渡された値はすべての `groupInput` に注入される。`groupOutput` が複数あるときは、ソケットごとにそれを配線している最初の `groupOutput` の値が外部出力になる(どれにも配線されていなければ最初のノードのソケットの既定値)。`groupInput`/`groupOutput` はどちらも省略可(`defineGroupNode()` は `internalNodes` にこれらのノードが無くてもエラーにしない)で、省略すれば(中に入って削除した場合も)そのグループの外部入力/出力ソケットはそれぞれ0個になる(`resolveNodeSockets()` は型の静的な `inputs`/`outputs` へ戻さない — 戻すと値の注入先が無いのに入力が見え続ける) — 既存14種のガーメントの `groupInput` は、他ガーメントと共有される値(`anchorY`・体の半径・`headRadius` など)と `color` だけをソケットに持ち、どれも `groupOutput`(下記参照)を含めていない(描画は `sceneOutput` が別途担うため出番が無い)。
  - `groupInput` ノードの各ソケットは、未接続時のリテラルなデフォルト値(`socket.default`)を `defineGroupNode()` の登録時テンプレート、または `groupIOSocket.ts` の `defaultForSocketType()`(`GroupInputNode.tsx`/`GroupOutputNode.tsx` の `addSocket()` がソケット追加時に型ごとに割り当てる初期値: number は `0`、color は `'#cccccc'`)から持つ。**デフォルト値は `Group Input` ノード上では表示されず、編集もできない**(number/color とも。値は `defineGroupNode()` のテンプレート、色は `colorSocket()` の既定色で決まり、変更はグループカードの未接続入力の欄で行う)。このデフォルト値は、そのグループインスタンスのグループカードの未接続入力の欄の初期値にもなる(グループカードの欄に入れた値はインスタンスの `data[socketId]` に持たれ、これを上書きする)。geometry/material ソケットにはリテラルなデフォルトが無い(未接続なら単に出力されない)。
  - `groupOutput` ノードは、配線された各入力ソケットの値をそのまま素通しする(`editor/nodeComponents/GroupOutputNode.tsx`)だけの、`groupInput` と対称なノード。**含めた場合、グループ本体のこの出力はすべてこのノードに実際に配線された値だけになり、このノードの責務は「配線されたものをまとめて外へ出す」ことだけ**。**既存14種のガーメントはどれも `groupOutput` 自体を internalNodes に含めていない**(geometry/material の描画は `groupOutput` ではなく、下記の `sceneOutput` ノードが専用に担うため出番が無い)。他ガーメントから再引きされたい値があれば、`groupOutput` を追加してそこへ配線し、ソケットを公開できる — ただし「あるガーメントの内部値を、別のガーメントだけが特別に覗き見る」という設計は、その値が実は複数ガーメントで**共有**されるべきものだった場合には筋が悪い(下記「値が複数グループで共有される場合」参照)。
  - **配置情報の生成(`garmentPlacement` の `offsetY` 入力欄)/配置の焼き込み(`garmentPlacement`)の分離**: offsetY のための専用ノード型は無く、各 `<name>GroupNode.ts` は `garmentPlacement` の `offsetY` 入力欄(`garmentOutput()` の `offsetY`)に値を持たせ、これと外部ソケット `anchorY`(ルートの `bodyLayout` 共有ノードが計算した5つのアンカー候補 — `waistY`/`shoulderY`/`feetY`/`wristY`/`headCenterY` — のうち、そのガーメントが実際に使う1つが配線されている、下記「値が複数グループで共有される場合」参照)を `garmentPlacement`(`nodes/definitions/generic/garmentPlacement.ts`)が受け取る。`garmentPlacement` は geometry とこの2つの値を受け取り、`numberAdd`(anchorY + offsetY)→`translate`(`bodyGroup` が胴体/頭/腕/脚の配置に使っているのと同じ、Y だけを配線して平行移動するだけの汎用ノード)という2ノードだけで geometry の頂点そのものを平行移動する — Blender の Geometry Nodes で「別オブジェクトの位置をサンプリングして Translate Geometry に渡す」のと同じ考え方で、取り付け位置をノードグラフの外側を流れるメタデータとして運ぶのではなく geometry の頂点座標に焼き込む。この結果、`sceneOutput`(そして最終的に `Garments.tsx`)は anchorY/offsetY を一切知る必要が無く、常に「原点に置けば正しい位置になる」geometry+material の2つだけを扱えばよい。どのアンカーを使うかは `bodyLayout → <name>Group.anchorY` という配線そのものが仕様であり、実行時に選択する仕組みは無い。同様に、「体に触れる半径」を求める「体の半径(`input.torsoRadius`/`legRadius`/`armRadius`/`neckRadius`)× 倍率」の `scale`(12種)は `bodyRadiusScale(radius, ratio)` で、`easedLatheCurve`→`latheGenerator` の定型(skirt/hat/gloves/pants/shoes/socks の6種)は `latheBody({ genId, direction, steps, startRadius, endRadius, distance })` で、肩の丸みで首まわりまで閉じた上衣のプロファイル(top/dress/jacket の3種、`generic/shoulderedProfile.ts`)は `shoulderedBody({ length, hemRadius, neckOpeningRatio })` で(いずれも `nodes/definitions/garmentParts.ts`)、ノードと配線を生成して展開している(`input` が同じグループ内に存在することが前提。`startRadius`/`endRadius`/`distance` は他のノードの id かリテラルの数値、`segments` はリテラル)。`material`(色は外部ソケット `color`)・`garmentPlacement`(`offsetY` は入力欄)・`sceneOutput` からなるこの「末端」のノードと配線は、全14種が `nodes/definitions/garmentOutput.ts` の `garmentOutput({ color, offsetY, geometry })` で生成して `internalNodes`/`internalEdges` へ展開している(`geometry` には最終的な geometry を出力するノードの id を渡す)。`<name>GroupNode.ts` の配線は `gen.geometry → placement.geometry`、`input.anchorY → placement.anchorY`、`placement.geometry → sceneOut.geometry`、`material.material → sceneOut.material` という順になる(`groupOutput` 自体を internalNodes に含めていないため、geometry/material がそちらへ配線されることはない — 下記参照)。
  - ソケットの追加は各ノードカード下部の型セレクタ+「+ Add」ボタン、削除は各行の「×」ボタン(`useGraphStore().removeGroupIOSocket(nodeId, socketId)`、下記参照)。ソケットの型は追加時に固定され、後から変更する仕組みは無い(型を変えたい場合は削除して追加し直す — Blender のようにドラッグで繋いだ相手の型を推測してソケットを生成する機能は無い)。
- **テンプレートの更新検知と追従**: 編集済み(実体化済み)のインスタンスは内部グラフを独立コピーとして持つため、テンプレートの構造を変えても自動では追従しない。`nodes/groupTemplate.ts` の `fingerprintGroupStructure()` が、内部ノードの id/型・エッジ・`groupInput`/`groupOutput` のソケット構成だけから構造の指紋を計算する(パラメータの値・座標は含めないので、値の調整では変わらない)。`defineGroupNode()` が登録時にテンプレートの指紋を記録し、`createDefaultData()` は実体化時にそれを `data.templateFingerprint` として保存する。`isGroupInstanceStale(type, data)` が保存された指紋(無い古いインスタンスは内部構造そのものの指紋)と現在のテンプレートを比べて「古い」を判定し、`GenericNode.tsx` のカードに「テンプレート更新あり」、`PresetPanel.tsx`(グループの中)に「テンプレートへ更新」ボタンを出す。更新は `migrateGroupToTemplate()`(`graphStore.ts` の `migrateCurrentGroupToTemplate`)が最新のテンプレートを読み込み直し、同じ id・同じ型のノードの値(入力欄・`groupInput`/`groupOutput` のソケットの既定値を含む)だけを引き継ぐ(配線の編集は失われ、対応するノードが無くなった値は捨てる。値の置き場所が別のノードへ移った場合の追跡はしない、詳細は `migrateGroupToTemplate()` のコメント)。グループ内部のプリセットも保存時の指紋(`Preset.templateFingerprint`)を持ち、読み込み時に古ければ値を引き継いだ更新を選べる。
- **内部配線はノードインスタンスごとに独立してキャンバス上で編集できる**。`GroupNodeConfig`(`internalNodes`/`internalEdges` — `inputs`/`outputs` フィールドは無く、`internalNodes` 内の `groupInput`/`groupOutput` ノードの `data.sockets` から `defineGroupNode()` が登録時に静的な `inputs`/`outputs` を自動導出する)自体は型ごとの固定テンプレートだが、`createDefaultData()` はこのテンプレートを `structuredClone()` した `{nodes, edges}` を返し(`nodes/autoLayout.ts` の `computeAutoLayout()` で座標も自動算出)、ノードインスタンスの `data` に独立したコピーとして持たせる。`evaluate()` は `data.nodes`/`data.edges` があればそちらを優先し、無ければ(`initialGraph.ts` の既存インスタンスのように)`config.internalNodes`/`internalEdges` にフォールバックする。パレットから同じ型を複数回追加しても、あるいは既存の `copySelected`/`pasteClipboard`/`duplicateSelected`(いずれも `structuredClone` ベース)で複製しても、各インスタンスは互いに独立している。
  - **編集UX**: `editor/nodeComponents/GenericNode.tsx` でグループノード(`category:'group'`)のタイトル行の「→」ボタンを押すと `useGraphStore().enterGroup(id)` が呼ばれ、キャンバスがそのインスタンスの内部だけの表示に切り替わる(Blender/Houdini方式、React Flow標準の `parentId`/`extent` によるインライン常時表示ではない)。`editor/BreadcrumbPanel.tsx` が現在の階層パスを表示し、クリックで任意の階層(`exitToLevel`)またはトップレベルへ戻れる。中に入っている間の `onNodesChange`/`onConnect`/`addNode`/`updateNodeData`/Undo/Redo/コピペといった編集操作は、`state/graphStore.ts` の既存アクションを一切改修せずにそのまま使っている(`enterGroup`/`exitGroup` がストアの `nodes`/`edges` を丸ごと差し替えるだけなので、既存アクションからは「今どの階層を編集しているか」を区別できない)。多段ネスト(グループの中の別グループ)も自然に成立する。`editor/NodePalette.tsx` は `scopeStack.length > 0`(=グループの中に入っている)の場合だけ Group Input/Output を一覧に含める — トップレベルに置いても意味を持たないため。
  - **落とし穴**: グループの中に入っている間、`state/graphStore.ts` の `nodes`/`edges` は「今開いている階層」の内部ノードだけになるため、これを直接見るコードは他ガーメントの消失やボディスケールのリセットを引き起こしうる。トップレベル視点の完全なグラフが必要な箇所は代わりに `rootEvaluatedResults`(`composeRootGraph()` 経由)を見る必要がある — 詳細・対象箇所・回避策は `src/state/CLAUDE.md` の「グループの中に入る」節を参照。
  - **`removeGroupIOSocket(nodeId, socketId)`**(`state/graphStore.ts`): `groupInput`/`groupOutput` ノードのソケットを1つ削除する専用アクション。単なる `updateNodeData()` と違い、(1) 同じハンドルidを参照する現在階層の内部エッジ、(2) グループの中に入っている場合、そのグループノード自身は現在の `nodes` には無く直近の `scopeStack` フレームに退避されているため、そのフレームの `edges`(親ノードから見た外部接続)の中で同じハンドルidに繋がっている外部エッジ、の両方も同時に削除する。外部エッジが残っている場合は削除前に確認ダイアログを出す(孤立エッジ — ハンドルが消えて繋がって見えないエッジ — を防ぐ、上記「グループの中に入る」の落とし穴と同種の対策)。`groupInput`/`groupOutput` ノード自体を削除した場合も同じく、`NodeEditor.tsx` の `onBeforeDelete` が確認し、`onNodesChange` が1つ上の階層の外部エッジを削除する(対象の判定は `externalEdgesOrphanedByRemoval()`)。`exitGroup()` 時の書き戻し(`{...n.data, nodes, edges}`)は `nodes`/`edges` だけ上書きするため、内部の `groupInput`/`groupOutput` ノードの `data.sockets` の変更はそのまま親ノードへ引き継がれる。
- `evaluate()` は、外部から渡された入力値(`inputs: Record<string, SocketValue>`)を埋め込みサブグラフ内の `groupInput` ノードの `data.injected` へ評価のたびに一時的に注入してから(`data` として永続化されるわけではない、この1回の `evaluateGraph()` 呼び出し限りのパッチ)、`evaluateGraph()` を**再帰的に**呼ぶだけ。未接続の外部ソケットは `inputs` に現れないため、`groupInput.evaluate()` 側で各ソケット自身の `default` にフォールバックする。`groupInput` ノード自体が無い場合はこの注入先が無いため、`inputs` に何を渡しても単に無視される(そもそも `def.inputs` が空なので外部から接続しようがない)。
- **注入できる型に制限は無い**(`groupInput` ノードの出力ソケットとして SocketValue をそのまま流し込むだけなので、geometry/material も注入できる)。ただし実際に使う既存14種は、他ガーメントと共有される値(体の半径 `torsoRadius`/`legRadius`/`armRadius`/`neckRadius`、取り付けアンカー座標の `anchorY`、bodyGroup と pants/shoes/socks が共有する `legSpacing`、bodyGroup と gloves が共有する `shoulderSpacing`(gloves では `armSpacing`)、bodyGroup と hat/glasses が共有する `headRadius`)だけを外部入力にしており、ガーメント固有の生パラメータは外部入力にせず埋め込みサブグラフ内部のノードの入力欄の値(複数のノードが共有する値だけ `numberInput`/`colorInput` ノード)として保持している(色は例外で、全ガーメントと `bodyGroup` が外部ソケット `color`(`garmentOutput.ts` の `colorSocket()`)を持ち、グループカードの入力欄から調整する)(ルート [`CLAUDE.md`](../../CLAUDE.md) の「Body(3Dモデル本体)も他14種のガーメントと同じ `<name>Group` ノードで組み立てられる」節参照)。**Height/Shoulder のスケールはどのガーメントグループにも直接配線されていない** — `bodyDimensionsGroup` の外部ソケット(`heightScale`/`shoulderScale`)としてのみ存在し、ルートでは配線せず `bodyDimensions` のグループカードの入力欄から調整する。アンカー座標の計算は `bodyDimensions`/`bodyLayout` という2つのトップレベル共有ノードが担うため、各グループが直接必要とするのは計算済みの `anchorY`(1個の数値)だけになる。ガーメント自身の「体に触れる半径」を持つ12種(bag/belt/dress/gloves/jacket/necktie/pants/scarf/shoes/socks/skirt/top。necktie は前面の深さ、bag は体の側面の位置と前面の深さ)は、それが追従する体の半径(胴体: skirt/belt/dress/top/jacket/necktie/bag と pants の腰・scarf の垂れの前後位置、首: scarf の輪、脚: pants の裾/shoes/socks、腕: gloves と top の袖)を `bodyDimensions` から外部ソケット(`garmentParts.ts` の `bodyRadiusSockets`)で受け取り、グループ内部の `scale` の `Value` 入力欄の倍率を掛ける。倍率にしているのは、体型の比率を変えたとき(胴を細くする、など)に服が体と一緒に追従するため。
- **値が複数グループで共有される場合は、その値をどちらかのグループの内部に閉じ込めて `groupOutput` で覗き穴を開けるのではなく、`bodyDimensions` と同じく `src/state/initialGraph.ts` 側のトップレベルの共有ノードへ引き上げ、各グループへ普通の外部ソケットとしてファンアウトすること**。`bodyDimensions` が計算する脚の間隔 `legSpacing`(bodyGroup と pants/shoes/socks が共有する)・肩幅 `shoulderSpacing`(bodyGroup と gloves が共有する)・頭半径 `headRadius`(bodyGroup と hat/glasses が共有する)・胴体/脚/腕の半径(bodyGroup と12種のガーメントが共有する)がこの例。一方、同じグループの中だけで使い回す値(top の Torso Radius と Color を Top 本体と袖が共有する場合など)は共有ノードにせず、グループ内部の1つのノードから内部の複数の生成ノードへ配線すればよい(`topGroupNode.ts` 参照)。
- **`sceneOutput` はグループの埋め込みサブグラフの中に置く**(既存14種すべてがこの形)。**1つのグループの中に `sceneOutput` は何個置いてもよい**。中に入って `sceneOutput` ノードを `garmentPlacement`/`toonMaterial` などから配線すると、`groupNodeFactory.ts` の `evaluate()` が内部の `findResolvedSceneOutputs(internalNodes, internalResults)` を呼び、`internalNodes` を先頭から順に見て、見つかった解決済みの geometry+material の組をすべて集める。1つのノードから見つかる形は2通り: (1) `type === 'sceneOutput'` のノード自身(`groupOutput` を探すのと同じ、型名によるパターン)— その評価結果が geometry+material の両方を持っていれば採用する(1つのグループの中に複数あってもよいので、1つ見つけても探索は続ける)。(2) それ以外の任意のノード(典型的にはネストした別のグループノードインスタンス)— その評価結果が既に `sceneOutputGeometry<N>`/`sceneOutputMaterial<N>`(そのノードがさらに1つ内側から転送してきた予約キー、1組とは限らない)を持っていれば、そのすべてを採用する。集まった組を先頭から 0,1,2,... と振り直し、`sceneOutputGeometry<N>`/`sceneOutputMaterial<N>` という予約キーでグループ自身の外部出力(`groupOutput` があればその転送分と同じ Record、無ければ空オブジェクトへ追加)へ加える。このキーはグループの静的な `outputs`(`groupOutput` があればその `data.sockets` から導出される、パレット上で見える入出力ソケット)には含まれず、他ノードへ配線するための一般的なソケットではない — `Garments.tsx` だけが読む専用チャンネル。`Garments.tsx` はグループの型を問わずこのキーが1つでもあれば、見つかった数だけ独立した `ToonMesh` として描画する(上記「出力カテゴリのノード」節、`src/scene/CLAUDE.md` 参照)。この内部配線を消してしまう(または `sceneOutput` ノード自体・その入力を削除してしまう)と、そのメッシュは単に描画されなくなる(フォールバックを持つ中継ノードは無い)。`anchorY`/`offsetY` はこの経路には一切乗らない — `garmentPlacement` が内部で消費してジオメトリの頂点座標へ焼き込むため、`input.anchorY`/`offsetYIn → garmentPlacement` の配線を消すと(`garmentPlacement` 自身もフォールバック `anchorY: 0`/`offsetY: 0` を持つので)取り付け位置だけが原点付近のデフォルトに戻り、描画自体は消えない。**多段ネスト(グループの中の別グループ)にも対応している** — 各階層の `evaluate()` が同じ `findResolvedSceneOutputs()` を呼ぶだけなので、孫グループの内部 `sceneOutput`(複数でも)は子グループを経由して祖父グループまで、何階層でも自動的に転送・再インデックスされる(特別な再帰処理は無く、`groupNodeFactory.test.ts` の「多段ネスト」ケースで検証している)。インデックスの割り当て順は `internalNodes` の並び順で決まり、優先順位を隠し持たない。
- **空から組む自作グループ `customGroup`**(`groups/customGroupNode.ts`、パレットでは「Group」見出し): 中身が Group Input(左)と Group Output(右)だけの空のグループ。中身はインスタンスごとの独立コピーなので、置いた1個1個が別々の自作グループになる(Blender のような定義の共有は無い)。`defineGroupNode()` の `userDefined: true` で定義し、テンプレートの構造の指紋を登録しない(中身の編集が常に「テンプレート更新あり」と判定されるのを防ぐ — 指紋が無い型は `isGroupInstanceStale()` が常に false)と同時に `renamable` になり、インスタンスごとの表示名を `data.label` に持つ(`editor/CLAUDE.md` 参照)。`internalNodes` に `position` を書いたノードは自動レイアウトせずその座標に置く(空のグループでは自動レイアウトだと Input/Output が縦に並ぶため)。
- 新しいガーメント種をこのパターンで追加する手順は `add-garment-type` スキルを参照。

## 汎用ノード一覧(特定のガーメント/パーツに紐付かないノード)

新しいノードを書く前に、`nodes/definitions/` と `nodes/definitions/generic/` に近い処理をする汎用ノードが既に無いか確認すること — 専用ノードの重複実装を後から統合し直す手戻りを避けるため(pants/shoes/gloves/socks の左右対称ペア化が `mirrorPair` に統一されているのがその例)。ノードの一覧は `ls` で分かるので、ここには一覧では分からない点だけを書く。

- `mergeGeometry` は入力ソケット `geometries` に繋いだすべての geometry を結合する(複数接続できるソケットなので、パーツの増減は配線を足す/切るだけ。1つだけならそのまま出力する)。uv の有無だけが違う geometry は uv を外して結合する — 標準プリミティブは uv を持ち、手組みのチューブ/リンググリッドは持たないが、トゥーンシェーディングは uv を使わないため。
- **回転体のプロファイルは `curve` 型で運ぶ**: `easedLatheCurve`(`geometry/latheProfile.ts` の `EasedLatheCurve`)が、アンカーから反対側の端まで半径をイージングしながら結ぶ `(半径, 高さ)` の曲線を出力し、`latheGenerator`/`ringGridGenerator`(最上段にネックラインを彫り込んだ手組みのチューブ、top/dress が使う)が、入力欄 `Profile Steps` 個に分割した点列(`getPoints(steps)`)から回転体を作る(分割数は曲線ではなく受け取る側の設定)。向きは数値では指定せず、出力ソケット `Curve Up`(アンカーから上へ)/`Curve Down`(アンカーから下へ)のどちらを配線するかで選ぶ(`necklineShapes` の形の選択と同じ)。どちらの向きも `t` が増えるほど下から上へ進む。belt/scarf の `bulgedBand` は、上下2つのプロファイルを `concatCurve`(前半が `curveA`、後半が `curveB`、つなぎ目の点は重複しない)で連結し、`Profile Steps` を上下それぞれの分割数の2倍にする。 `ellipticLatheCurve` は同じ入出力で、半径を楕円の 1/4 で変える(アンカー側で水平、反対端で垂直)。
- `curve`(`THREE.Curve<THREE.Vector2>`)は、`t`(0〜1)から平面上の点を返す曲線を運ぶソケット型。ネックラインの重みは `(t, f(t))`(`geometry/functionCurve.ts` の `FunctionCurve`)、回転体のプロファイルは `(半径, 高さ)`(`EasedLatheCurve`)。点列に分割せず、必要な位置でだけ評価する(分割数による近似や補間の誤差が無い)。`rampCurve`(`y = t`)/`scaleCurveY`/`translateCurveY`/`multiplyCurveY`(いずれも入力の曲線の x は変えずに y だけを加工した新しい曲線を返す)を配線で組み合わせて、x を横軸とした任意の曲線を組み立てる。
- `profileCurve` は、高さを 0〜`length` の 8 等分にした 9 点の半径(`radius` の `r0`〜`r8` 倍。細かい形には 13・17・25・33 点の `profileCurve13`/`17`/`25`/`33` があり、部位ごとに選ぶ)をなめらかにつないだ `(半径, 高さ)` の `curve` を出力する。補間は半径の2乗に対する曲率連続の3次スプライン(`geometry/splineProfile.ts`)で、`r0`/`r8` を 0 にすると端が球の極のように丸く閉じ、制御点が球の上にあれば球の輪郭をそのまま再現する。`loftGenerator` は `latheGenerator` と同じく `profile`(X の半径)を分割した回転体を作り、`depthProfile`(Z の半径の曲線、未接続なら円断面)を同じ高さで引いた比で各リングの Z を伸縮して楕円断面にする(曲線は同じ高さの範囲を持つこと)。`dropProfile`(任意の曲線)を繋ぐと、各高さのリングを全周まとめて曲線の値だけ下げる(頭の下面)。`offsetZProfile`(符号付きの曲線 `signedProfileCurve`、任意)を繋ぐと、各高さのリングを丸ごと前後へずらす(胴体の前後非対称は、前後別々の半径だと継ぎ目に稜線が立つので、1つの楕円のずらしで表す)。`tiltProfile`(符号付きの曲線、度数)を繋ぐと、各高さの輪を中心まわりに前後へ傾ける(首の輪を軸に垂直にする)。`ringProfile`(`ringSpacingCurve`)を繋ぐと、輪の高さの割合を曲線で決める(頭が使う)。
- `numberDisplay`/`colorDisplay` は入力された number/color を表示するだけのノード。`outputs` は宣言せず(他のノードへは配線できない)、`evaluate()` が入力値を評価結果にだけ載せ、専用のカード(`editor/nodeComponents/`)がそれを読んで表示する。
- `glassesLensPair`/`glassesTemplePair`/`glassesBridge` は、`glassesGroup` を3つのパーツに分けたグループノード(レンズ・テンプル・ブリッジ)。3パーツが共有する値(`lensRadius`/`lensSpacing`/`forwardDepth`)は外部ソケットで受け取り、1つのパーツだけが使う値(ブリッジ/テンプルの太さなど)はグループの内部に持つ。
- **ネックラインの形(square/v/round)はノード構成で選ぶ**: `ringGridGenerator` の `necklineWeights`(`curve` 型、x=正面からの角度を 0〜1 に正規化した値、y=落ち込み量の重み)へ繋ぐ曲線の作り方で決まる。`necklineShapes` グループ(`generic/necklineShapes.ts`)が、共有の `rampCurve` を土台に square(0倍して+1)/v(-1倍して+1、`1 - t`)/round(自乗してから同様に `1 - t²`)の3つの加工チェーンを内包し、top/dress がグループとして1枚のカードで使っている(出力は `squareShape`/`vShape`/`roundShape`)。デフォルトは `roundShape → gen.necklineWeights` で、`vShape`/`squareShape` へ配線を付け替えると襟ぐりの形が切り替わる。未接続なら襟ぐりを彫り込まない。
- `taperedEllipseTubeGenerator`/`taperedRectTubeGenerator`(`geometry/taperedTube.ts`)は断面の形が使うノードタイプで決まる(ソケットで形を選ぶ仕組みは無い。袖は楕円、ネクタイのブレードは矩形)。`alignedBoxGenerator`(`geometry/alignedBox.ts`、2点間を結ぶよう回転+平行移動した Box、剛体変換のみなので巻き順は保たれる)は始点・終点をそれぞれ X/Y/Z の3ソケットに分解している(bag のストラップ、glasses のブリッジ/テンプル)。
