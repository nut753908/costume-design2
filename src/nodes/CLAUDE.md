# src/nodes/ のガイダンス

全体のアーキテクチャ概要は[ルートの CLAUDE.md](../../CLAUDE.md)を参照してください。

## ノードグラフエンジン

React Flow (`src/editor/`) は UI の状態(ノードの位置、選択、ドラッグ)のみを保持します。実際の計算は、React Flow について何も知らない別の純粋関数レイヤーが担当します。

- `nodes/types.ts` — ソケットの型システム(`SocketType`: number/color/enum/geometry/material/points。入力ソケットの `SocketDef.multiple` が true なら複数のエッジを接続でき、`evaluate()` にはエッジの並び順で集めた値が `{ type: 'geometries' }` として渡される — 現在は `mergeGeometry` の `geometries` だけが使う)と `NodeTypeDefinition`(`inputs`/`outputs` ソケットと `evaluate(inputs, data) -> outputs` 関数を宣言)。`GraphNode`/`GraphEdge` もここで定義されており、React Flow 自身の `Node`/`Edge` 型から切り離された最小限の形になっているため、evaluator は UI ライブラリなしでも利用・テスト可能です。`points`(`THREE.Vector2[]`)は `easedLatheProfile`(`nodes/definitions/generic/easedLatheProfile.ts`、Lathe用のプロファイル点列を生成)→`latheGenerator`(`nodes/definitions/generic/latheGenerator.ts`、points から生の `THREE.LatheGeometry` を作る)という生成〜消費の間を流れる値のための型で、geometry/material と同じくリテラルなデフォルトを表現できません(`groupIOSocket.ts` の `literalGroupInputValue()` 参照)。`translatePointsY`/`slicePoints`/`concatPoints`(`nodes/definitions/`)は、`beltGroupNode.ts` が2つの `easedLatheProfile` の結果を連結する際に使う、points を直接操作する汎用ノード(`translateY`/`mergeGeometry` の points 版)。色は `editor/socketColors.ts` の `SOCKET_COLORS` に追加してあります。
- `nodes/registry.ts` — `registerNodeType()` / `getNodeType()`。すべてのノードタイプ(入力、ジェネレーター、マテリアル、出力)はここに自身を登録します。`src/nodes/definitions/*.ts` が実際のノードタイプの実装であり、`definitions/index.ts` がそれらすべてを副作用インポートしてレジストリを埋めます。
- `nodes/evaluateGraph.ts` — evaluator 本体。ノードをトポロジカルソートし(Kahn のアルゴリズム、循環がある場合は `GraphCycleError` を投げる)、順番に各ノードの `evaluate()` を評価します。**未接続の入力ソケットは、そのノード自身のリテラルな `data[socketId]` の値にフォールバックします** — これは Geometry Nodes で未接続のソケットがウィジェットのデフォルト値を使うのと同じ挙動であり、単独の(未接続の)ノードでも動作するようにするための中心的な仕組みです。この未接続ソケットの解決ループは `nodes/resolveNodeSockets.ts` の `resolveNodeSockets(type, data)` を経由します(型の静的な `inputs` ではなく、グループノードインスタンス内部の `groupInput`/`groupOutput` ノードの `data.sockets` があればそちらを優先する — グループノードの動的ソケット用、下記「グループノード」節参照)。

  **ノード単位のメモ化キャッシュ**: `evaluateGraph()` はモジュールレベルの `WeakMap`(キーは各ノードの `node.data` オブジェクトそのもの)で、直前に評価したときの解決済み `inputs` と結果を覚えている。ある呼び出しで、あるノードの `node.data` 参照が前回と同じ(= 編集されていない)、かつ解決済み `inputs` も前回と値が同じであれば、`def.evaluate()` を呼ばずに前回の結果オブジェクトをそのまま返す。`number`/`enum`/`color` は値そのもので比較し、`geometry`/`material`/`points` は参照比較のみ(構造の深い比較は再計算とコストが変わらないため)——生成元のノードもキャッシュヒットして同じ参照を返している限り、この参照比較は連鎖的に成立する。`state/graphStore.ts` の全アクションはイミュータブルな更新しか行わず、変化していないノードは常に同じ `data` 参照を保つ(`src/state/CLAUDE.md` 参照)ため、これが「このノードは編集されていないか」の安価な判定として機能する。`evaluateGraph()` は最上位の呼び出し(`state/useRootEvaluatedGraph.ts` 等)からグループノードの埋め込みサブグラフの中(`groupNodeFactory.ts` の `evaluate()` が呼ぶ再帰呼び出し)まで同じ実装を共有しているため、このキャッシュも階層を問わず一様に効く——トップレベルで1つのスライダーを動かしても、それに依存しない他のグループは `groupNodeFactory.ts` の `evaluate()` 自体(＝内部サブグラフのフル評価)がまるごとスキップされる。`WeakMap` にしているため、ノードが削除されて `data` オブジェクトがどこからも参照されなくなれば対応するキャッシュエントリも GC に任せて自動的に回収され、手動の無効化ロジックは不要。キャッシュのヒット/ミスの累計は `getNodeEvalCacheStats()` で読め、`App.tsx` の右下の `evaluations` カウンターの隣に表示している(グループ内部の再帰評価分も含む累計で、例えば無関係なスライダーを動かしたときにミスが増えず、ヒットだけが増えることで効いているかを確認できる)。
  - **`data` のミューテートへの備え**: キャッシュエントリは登録時点の `node.data` のトップレベルの浅いスナップショットも持ち、ヒット判定で現在の `data` と比較する。参照が同じでも誰かが `data` のトップレベルのフィールドを直接書き換えていればヒットさせず再評価する(このアプリの更新経路は常にイミュータブルなので通常は起きない)。ネストしたオブジェクト(グループノードの `data.nodes` の中身など)の直接ミューテートまでは検知しないため、更新は必ず新しいオブジェクトを作って差し替えること。
- **このキャッシュが正しく働くための前提**: 各ノードタイプの `evaluate(inputs, data)` は `inputs`/`data` だけに依存する純粋関数であり続けること(隠れたグローバル状態を読まない)、そして `inputs` として受け取った `geometry`/`material`/`points` を(`.clone()` 等せずに)直接ミューテートしないこと。既存の全ノード実装は最初からこの前提を満たしている(`translateY.ts`/`translateX.ts`/`translateZ.ts`/`scaleZ.ts` が入力ジオメトリを `.clone()` してから変換するのがその一例)が、新しいノードタイプを追加する際もこの2点を破らないこと——破ると、キャッシュが返す「前回の結果への参照」が呼び出し元の意図しない形で書き換わり、無関係な箇所に伝播しうる。
  - **テストへの影響**: `getNodeType(type).evaluate(...)` を同じ型・同じ inputs で複数回呼ぶテスト(特に内部で `build*Geometry()` を spy する `topGroupNode.test.ts`/`dressGroupNode.test.ts`/`necktieGroupNode.test.ts` のようなテスト)は、キャッシュヒットにより2回目以降 `evaluate()` 自体が呼ばれず spy が発火しないことがある。`src/testSetup.ts` が全テストの `beforeEach` で `resetNodeEvalCacheForTests()`(`evaluateGraph.ts` がテスト専用に export)を呼び、キャッシュを毎回空にしてテストどうしを独立させている(`vite.config.ts` の `test.setupFiles` で配線、`evaluateGraph.test.ts` の「ノード単位メモ化」節にこのキャッシュ自体の検証がある)。
- 出力カテゴリのノードのうち `sceneOutput`(`nodes/definitions/generic/sceneOutput.ts`)は、描画専用の終端ノードです。`evaluate()` の戻り値(geometry+material をそのまま素通しするだけ)は、最終的には他のノードに消費されるのではなく `Garments.tsx` が `rootEvaluatedResults` から直接読み取ります。**必ず `<name>Group` の埋め込みサブグラフの中に置く**(既存14種すべてがこの形、下記「グループノード」節参照)。**1つのグループの中に `sceneOutput` は何個置いてもよい**(例: 「本体」と「フード」を1つのグループにまとめつつ別々のメッシュとして描画する、など)— `groupNodeFactory.ts` の `evaluate()` がこれらの内部 `sceneOutput` の評価結果を `sceneOutputGeometry<N>`/`sceneOutputMaterial<N>`(`N` は0始まりの連番、`nodes/definitions/generic/sceneOutput.ts` の `sceneOutputGeometryKey()`/`sceneOutputMaterialKey()`/`matchSceneOutputGeometryIndex()` が命名規則の唯一の真実の源)という予約キーへ転送し、グループ自身の外部出力に加える。`Garments.tsx` は `rootEvaluatedResults` の各エントリについて、ノードの型を問わずこのキーが1つでもあれば、見つかった数だけ独立した `ToonMesh` として描画する。これは「型が geometry+material を持っていれば自動描画される」という暗黙の検出ではなく、「明示的に `sceneOutput` へ配線されているか」が描画対象かどうかの仕様そのものになる(詳細は `src/scene/CLAUDE.md`)。`groupOutput` 自身の `geometry`/`material` ソケット(グループ間で値を再利用したい場合の汎用ソケット、現在は既定では未使用)にどんな値があっても、それだけでは描画対象にはならない — `Garments.tsx` は `groupOutput` 経由の通常出力を一切見ず、`sceneOutput` 経由の予約キーだけを見るため。

- Body(3Dモデル本体)は専用のノードタイプを持たない。他14種のガーメントと全く同じ `<name>Group` パターン(`bodyGroup`、`nodes/definitions/groups/bodyGroupNode.ts`)で表現されており、内部の `sceneOutput` を通じて上記の経路にそのまま乗る。胴体(`capsuleGenerator`)・頭(`sphereGenerator`)・腕1組/脚1組(`cylinderGenerator`+`mirrorPair`)の4パーツは1つの `mergeGeometry`(複数接続できる入力ソケット)へ配線して1つのジオメトリへ結合してから、`sceneOutput` 1個だけへ配線している(scarf が belt+box を `mergeGeometry` でまとめるのと同じ、複数プリミティブを1グループ内で完結させる形、下記「グループノード」節参照)。

## 新しいノードタイプの追加

手順は `add-node-type` スキルを参照してください。

`defineGroupNode()` のテンプレートで存在しないノード id/ソケット id を指すエッジを書いても、`evaluateGraph` は静かに無視して評価を続けるため実行時には気づけない。`nodes/definitions/groupNodeWiring.test.ts` が登録済みの全グループ型について、内部ノードの type が登録済みであること・内部エッジの端点が実在するノードの実在するソケットを指すこと・1入力に複数エッジが接続されていないことを走査して検証するので、グループを追加/配線し直したらこのテストで確認できる。

## グループノード

`nodes/definitions/groupNodeFactory.ts` の `defineGroupNode()` は、複数の既存ノード(`numberMultiply`+generator+`toonMaterial`+`enumInput`/`numberInput`+`garmentPlacement` など)を1つの埋め込みサブグラフとして内包し、外部には限られた入出力ソケットだけを見せる「グループノード」を定義する。`category: 'group'` 固定(`NodeCategory` に追加済み、パレット/コンテキストメニューでは「Groups」セクションに表示される)。`src/state/initialGraph.ts` の全14種のガーメント(`<name>GroupNode.ts`、例: `skirtGroupNode.ts`)がこのパターンで定義されている(top は袖(`sleeveGenerator`)も内包し、Top 本体と袖を `mergeGeometry` で結合して1つの `sceneOutput` へ渡す)。Body(3Dモデル本体)も `bodyGroup`(`bodyGroupNode.ts`)として同じパターンに乗っており、ガーメント/Bodyを合わせて `src/state/initialGraph.ts` 直下には計15個の `<name>Group` ノードが存在する — ただし `bodyGroup` は `garmentPlacement`(下記参照)を使わない点が他のガーメントと異なる(Body には取り付けアンカーの概念が無く、`bodyLayout` が計算した Center Y をそのまま `translateY` へ渡すだけで済むため)。

`bodyGroup` は胴体(`capsuleGenerator`)・頭(`sphereGenerator`)・腕1組/脚1組(`limbPair`)という4つのパーツを内部に持ち、胴体・頭は `translateY`(Y座標を数値でそのまま受け取って平行移動するだけの汎用ノード)で配置してから、腕/脚とあわせて1つの `mergeGeometry` へ配線して1つのジオメトリへ結合し、`sceneOutput` 1個だけへ配線している(scarf が belt+box を `mergeGeometry` でまとめるのと同じ、複数プリミティブを1グループ内で完結させる形)。`gen` は Body 専用のジェネレーター型ではなく、`capsuleGenerator`/`sphereGenerator`/`cylinderGenerator`(`nodes/definitions/generic/capsuleGenerator.ts` 等、`geometry/primitives.ts` の `build*Geometry()` を THREE.js 標準プリミティブへそのままラップしただけの汎用プリミティブノード、`geometry/CLAUDE.md` 参照)という、Bodyに限らず使い回せるノードを使う。腕/脚は同じ構成の `limbPair`(`nodes/definitions/generic/limbPair.ts`、`bodyGroup` が腕用・脚用の2インスタンスを使う)で、テーパー円柱1本(`cylinderGenerator`)を `mirror`(`mirrorPair`、`nodes/definitions/generic/mirrorPair.ts`)で ±spacing だけ X方向に離した左右対称ペアへまとめ、`translateY` で配置する。同じ `mirror`(`mirrorPair`)は pants/shoes/gloves/socks の各 `<name>GroupNode.ts` でも使われている。`mirrorPair` 自身も単一ノードの `evaluate()` に処理を隠さず、`defineGroupNode()` で組んだグループノードになっている — 内部で `offset` を `negate`(`numberNegate`)で符号反転してから2つの `translateX`(`translateY` のX版、`translateX.ts`)へそれぞれ +offset/-offset として渡し、その2つの出力を `mergeGeometry`(`mergeGeometry.ts`、`mergeGeometries()`+`computeVertexNormals()` を切り出した汎用ノード)で1つに結合し、`groupOutput` からそのまま返す(このグループは `sceneOutput` を持たず、`groupOutput` で1つの `geometry` 値を外部へ再公開する側の使い方 — 下記「`groupOutput` ノードは...」節参照)。手首/足首側を根元よりわずかに細くするテーパー比率も、`bodyGroup` 内の腕用 `armTaperRatioIn`/脚用 `legTaperRatioIn`(ともに `numberInput`)を `limbPair` の外部ソケット `taperRatio` へ配線し、`limbPair` 内部で `taper`(`numberMultiply`)→`gen.radiusBottom` という可視の配線へ展開している(腕と脚それぞれ独立した値であることをラベルで明示している)。

トゥーンのアウトライン(`rendering/Outline.tsx`)はワールド原点基準の一様スケール複製(`<mesh scale={1 + OUTLINE_THICKNESS}>`)で実装されているため、4パーツを個別の `sceneOutput`(=個別メッシュ)として描画しても、`mergeGeometry` で1つに結合してから描画しても、最終的な頂点座標・見た目は変わらない — `bodyGroup` が `mergeGeometry` を使ってでも他のガーメントと同じ「1グループにつき必要な数だけの `sceneOutput`」という形を素直に選べる理由でもある。

**四則演算チェーンで使う定数(テーパー比率、固定の深さなど)は `numberMultiply`(`taper` を含む)自身の `data` にリテラルとして隠さず、必ず専用の `numberInput` ノード(`bodyLayoutGroupNode.ts` の `armTorsoOverlapRatioIn`/`feetYIn` と同じ形)として配置してから配線すること** — `numberMultiply`/`numberAdd`/`numberSubtract` は `data.label` の編集こそできても値そのものを編集するUIを持たないため、そうしないと値がキャンバス上のどこにも見えなくなる。値がユーザー調整可能なスタイルパラメータの場合(`armTorsoOverlapRatioIn` など)はそのまま `numberInput` リテラルを書けばよいが、`min`/`max`/`value` を同じ値に固定して事実上変更不能にする「常に一定の値を持つ `numberInput`」(0/1/-1、Bulge/Front Depth のような固定値)は `nodes/definitions/constNumberInput.ts` の `constNumberInput(id, value, label)` ヘルパーで定義する(このイディオムのコピペを防ぐための共通化、scarf/bag/skirt/jacket/belt/glasses/`mirrorPair`/`bodyLayoutGroupNode.ts` の `feetYIn` などで使われている)。

4パーツ間で共有される肌色(Material)は各ネスト用グループの内部に置かず、`bodyGroup` 自身の `skinColorIn`(`colorInput`)→`toonMaterial` から4つのネスト用グループそれぞれの外部ソケット `material` へファンアウトする(「値が複数グループで共有される場合」パターン、下記参照)。各ネスト用グループが内部の `sceneOutput` で解決した geometry+material は、`findResolvedSceneOutputs()` による多段ネストの転送(下記「`sceneOutput` はグループの埋め込みサブグラフの中に置く」節参照)で `bodyGroup` 自身の `sceneOutputGeometry<N>`/`sceneOutputMaterial<N>` へ自動的にバブルアップするため、`bodyGroup` 自身は `sceneOutput` を1つも持たない。

`bodyDimensionsGroup`(`bodyDimensionsGroupNode.ts`)/`bodyLayoutGroup`(`bodyLayoutGroupNode.ts`)という2つの `<name>Group` 型は、ボディの各部位の半径・長さ(9出力)と配置Y座標(8出力、うち `waistY`/`shoulderY`/`feetY`/`wristY`/`headCenterY` の5つはガーメントの取り付けアンカー候補を兼ねる)を計算する。「体に触れる半径」の scale 計算自体は他のガーメントと同じ `numberInput`(基準値)→`numberMultiply`(Height/Build/Shoulder のスケールを掛ける)の形で、`bodyDimensionsGroup` はこれを9個の部位パラメータぶん内部に持つ。Height/Shoulder のスケール(`heightScaleIn`/`shoulderScaleIn`)は `bodyDimensions` からしか参照されない単独パラメータのため内部の `numberInput` として持ち、`buildScale` だけは9ガーメントへも直接ファンアウトする共有値のため外部ソケット(`input.buildScale`)のまま(下記「値が複数グループで共有される場合」節参照)。胴体/頭/腕/脚のY座標配置も `numberAdd`/`numberSubtract`/`numberMultiply` の四則演算チェーンとして `bodyLayoutGroup` の内部に持つ。いずれもブラックボックスの計算ノードではなく、ダブルクリックで中に入れば実際の式がそのまま見える。`numberAdd`(`A+B`)/`numberSubtract`(`A-B`)は `numberMultiply` と対になる汎用の二項演算ノードで、`bodyLayoutGroupNode.ts` のY座標配置(`waistY + torsoCapsuleHeight/2` のような式)を組み立てるために存在する。

この2つは `bodyGroup` の専用物でも `garmentPlacement` の専用物でもなく、`src/state/initialGraph.ts` 側のトップレベル共有ノード(id: `bodyDimensions`/`bodyLayout`)としてただ1組だけ存在し、`bodyGroup` と全14ガーメントへ普通の外部ソケットとしてファンアウトされている(`bodyBuild` と同じ「値が複数グループで共有される場合はトップレベルの共有ノードへ引き上げる」パターン、下記「値が複数グループで共有される場合」節参照)。ルートキャンバス上には "Body Dimensions"/"Body Layout" という独立した2枚のカードが直接見え、ダブルクリックすればその中の実際の四則演算グラフが見える。

- **外部インターフェースは Blender の Geometry Nodes と同じく「Group Input」「Group Output」ノードそのものが定義する**。`nodes/definitions/groupInput.ts`/`groupOutput.ts`(`category: 'group-io'`、パレット/コンテキストメニューでは「Group I/O」セクション — グループの中に入っている間だけ表示される、下記編集UX参照)がこれらのノードタイプで、`data.sockets: GroupIOSocket[]`(`nodes/definitions/groupIOSocket.ts`)という動的なソケット一覧を持つ。`groupInput` は `data.sockets` がそのまま動的な**出力**ソケット一覧に、`groupOutput` は動的な**入力**ソケット一覧になる(`nodes/resolveNodeSockets.ts` がこの2つの型名を特別扱いする)。グループノード本体(`category:'group'`)が外部に見せる入出力ソケットは、埋め込みサブグラフ内にあるこの2ノードの `data.sockets` からそのまま転送される(`resolveNodeSockets()` が `data.nodes` の中から `type: 'groupInput'`/`'groupOutput'` のノードを探して転送する)。**中に入って、この2ノードにソケットを増減・配線するだけで、グループ本体の外部から見えるハンドルが増減する**。`groupInput`/`groupOutput` はどちらも省略可(`defineGroupNode()` は `internalNodes` にこれらのノードが無くてもエラーにしない)で、省略すればそのグループの外部入力/出力ソケットはそれぞれ0個になる — hat/bag/necktie/glasses は Anchor Y(取り付け位置)以外に他ガーメントと共有される値を持たないため `groupInput` の `data.sockets` は `anchorY` の1個だけで、既存14種のガーメントはどれも `groupOutput`(下記参照)を含めていない(描画は `sceneOutput` が別途担うため出番が無い)。
  - `groupInput` ノードの各ソケットは、未接続時のリテラルなデフォルト値(`socket.default`、enum の選択肢一覧 `socket.options` を含む)を `defineGroupNode()` の登録時テンプレート、または `editor/nodeComponents/GroupInputNode.tsx` の `addSocket()` 内 `defaultForType()`(ソケット追加時に型ごとに割り当てる初期値: number は `0`、color は `'#cccccc'`、enum は `'a'`・`options: ['a', 'b']`)から持つ。**これらは型を問わずノードカード上では一切編集できない**(値そのものを UI から直接いじる手段は無い — 変えたい場合はソケットへ配線して値を供給する)。geometry/material ソケットにはリテラルなデフォルトが無い(未接続なら単に出力されない)。
  - `groupOutput` ノードは、配線された各入力ソケットの値をそのまま素通しする(`editor/nodeComponents/GroupOutputNode.tsx`)だけの、`groupInput` と対称なノード。**含めた場合、グループ本体のこの出力はすべてこのノードに実際に配線された値だけになり、このノードの責務は「配線されたものをまとめて外へ出す」ことだけ**。`groupInput` と同じく省略可(`defineGroupNode()` は `internalNodes` にこのノードが無くてもエラーにしない)で、省略すればそのグループの外部出力ソケットは0個になる — **既存14種のガーメントはどれも `groupOutput` 自体を internalNodes に含めていない**(geometry/material の描画は `groupOutput` ではなく、下記の `sceneOutput` ノードが専用に担うため出番が無い)。他ガーメントから再引きされたい値があれば、`groupOutput` を追加してそこへ配線し、ソケットを公開できる — ただし「あるガーメントの内部値を、別のガーメントだけが特別に覗き見る」という設計は、その値が実は複数ガーメントで**共有**されるべきものだった場合には筋が悪い(下記「値が複数グループで共有される場合」参照)。
  - **配置情報の生成(既存の `numberInput` を流用)/配置の焼き込み(`garmentPlacement`)の分離**: offsetY のための専用ノード型は無く、各 `<name>GroupNode.ts` は `offsetYIn`(`numberInput`)をテンプレート内に置き、その `value` 出力を外部ソケット `anchorY`(ルートの `bodyLayout` 共有ノードが計算した5つのアンカー候補 — `waistY`/`shoulderY`/`feetY`/`wristY`/`headCenterY` — のうち、そのガーメントが実際に使う1つが配線されている、下記「値が複数グループで共有される場合」参照)と合わせて `garmentPlacement`(`nodes/definitions/generic/garmentPlacement.ts`)へ配線する。`garmentPlacement` は geometry とこの2つの値を受け取り、`numberAdd`(anchorY + offsetY)→`translateY`(`bodyGroup` が胴体/頭/腕/脚の配置に使っているのと同じ、Y座標をそのまま受け取って平行移動するだけの汎用ノード)という2ノードだけで geometry の頂点そのものを平行移動する — Blender の Geometry Nodes で「別オブジェクトの位置をサンプリングして Translate Geometry に渡す」のと同じ考え方で、取り付け位置をノードグラフの外側を流れるメタデータとして運ぶのではなく geometry の頂点座標に焼き込む。この結果、`sceneOutput`(そして最終的に `Garments.tsx`)は anchorY/offsetY を一切知る必要が無く、常に「原点に置けば正しい位置になる」geometry+material の2つだけを扱えばよい。どのアンカーを使うかは `bodyLayout → <name>Group.anchorY` という配線そのものが仕様であり、実行時に選択する仕組みは無い。同様に、Body Build でスケールする「生パラメータ × `input.bodyBuild`」の `scale`(10種)は `bodyBuildScale(rawId)` で、`easedLatheProfile`→`latheGenerator` の定型(skirt/jacket/hat/gloves/pants/shoes/socks の7種)は `latheBody({ genId, direction, steps, startRadius, endRadius, distance })` で(いずれも `nodes/definitions/garmentParts.ts`)、ノードと配線を生成して展開している(`segmentsIn` と `input` が同じグループ内に存在することが前提)。色・`offsetYIn`・`garmentPlacement`・`sceneOutput` からなるこの「末端」のノードと配線は、全14種が `nodes/definitions/garmentOutput.ts` の `garmentOutput({ color, offsetY, geometry })` で生成して `internalNodes`/`internalEdges` へ展開している(`geometry` には最終的な geometry を出力するノードの id を渡す)。`<name>GroupNode.ts` の配線は `gen.geometry → placement.geometry`、`offsetYIn.value → placement.offsetY`、`input.anchorY → placement.anchorY`、`placement.geometry → sceneOut.geometry`、`material.material → sceneOut.material` という順になる(`groupOutput` 自体を internalNodes に含めていないため、geometry/material がそちらへ配線されることはない — 下記参照)。
  - ソケットの追加は各ノードカード下部の型セレクタ+「+ Add」ボタン、削除は各行の「×」ボタン(`useGraphStore().removeGroupIOSocket(nodeId, socketId)`、下記参照)。ソケットの型は追加時に固定され、後から変更する仕組みは無い(型を変えたい場合は削除して追加し直す — Blender のようにドラッグで繋いだ相手の型を推測してソケットを生成する機能は無い)。
- **テンプレートの更新検知と追従**: 編集済み(実体化済み)のインスタンスは内部グラフを独立コピーとして持つため、テンプレートの構造を変えても自動では追従しない。`nodes/groupTemplate.ts` の `fingerprintGroupStructure()` が、内部ノードの id/型・エッジ・`groupInput`/`groupOutput` のソケット構成だけから構造の指紋を計算する(パラメータの値・ラベル・座標は含めないので、値の調整では変わらない)。`defineGroupNode()` が登録時にテンプレートの指紋を記録し、`createDefaultData()` は実体化時にそれを `data.templateFingerprint` として保存する。`isGroupInstanceStale(type, data)` が保存された指紋(無い古いインスタンスは内部構造そのものの指紋)と現在のテンプレートを比べて「古い」を判定し、`GenericNode.tsx` のカードに「テンプレート更新あり」、`PresetPanel.tsx`(グループの中)に「テンプレートへ更新」ボタンを出す。更新は `migrateGroupToTemplate()`(`graphStore.ts` の `migrateCurrentGroupToTemplate`)が最新のテンプレートを読み込み直し、同じ id・同じ型の `numberInput`/`enumInput`/`colorInput` の値だけを引き継ぐ(配線の編集は失われ、対応するノードが無くなった値は捨てる)。グループ内部のプリセットも保存時の指紋(`Preset.templateFingerprint`)を持ち、読み込み時に古ければ値を引き継いだ更新を選べる。
- **内部パラメータの露出**: 内部の `numberInput`/`colorInput`/`enumInput` は `data.exposed: true` を持つと、グループのカード上に操作行として表示される(UIは `editor/CLAUDE.md` 参照)。`groupTemplate.ts` の `listExposedParams(type, data)` が対象を返し、実体化済みなら `data.nodes`、未実体化ならテンプレートを見る。`garmentOutput()` の `colorIn`(全ガーメントの色)と `bodyDimensionsGroup` の `heightScaleIn`/`shoulderScaleIn` がテンプレート側で `exposed: true`。`exposed` は構造指紋に含まれず、`migrateGroupToTemplate()` は値と一緒に引き継ぐ。
- **内部配線はノードインスタンスごとに独立してキャンバス上で編集できる**。`GroupNodeConfig`(`internalNodes`/`internalEdges` — `inputs`/`outputs` フィールドは無く、`internalNodes` 内の `groupInput`/`groupOutput` ノードの `data.sockets` から `defineGroupNode()` が登録時に静的な `inputs`/`outputs` を自動導出する)自体は型ごとの固定テンプレートだが、`createDefaultData()` はこのテンプレートを `structuredClone()` した `{nodes, edges}` を返し(`nodes/autoLayout.ts` の `computeAutoLayout()` で座標も自動算出)、ノードインスタンスの `data` に独立したコピーとして持たせる。`evaluate()` は `data.nodes`/`data.edges` があればそちらを優先し、無ければ(`initialGraph.ts` の既存インスタンスのように)`config.internalNodes`/`internalEdges` にフォールバックする。パレットから同じ型を複数回追加しても、あるいは既存の `copySelected`/`pasteClipboard`/`duplicateSelected`(いずれも `structuredClone` ベース)で複製しても、各インスタンスは互いに独立している。
  - **編集UX**: `editor/nodeComponents/GenericNode.tsx` でグループノード(`category:'group'`)をダブルクリックすると `useGraphStore().enterGroup(id)` が呼ばれ、キャンバスがそのインスタンスの内部だけの表示に切り替わる(Blender/Houdini方式、React Flow標準の `parentId`/`extent` によるインライン常時表示ではない)。`editor/BreadcrumbPanel.tsx` が現在の階層パスを表示し、クリックで任意の階層(`exitToLevel`)またはトップレベルへ戻れる。中に入っている間の `onNodesChange`/`onConnect`/`addNode`/`updateNodeData`/Undo/Redo/コピペといった編集操作は、`state/graphStore.ts` の既存アクションを一切改修せずにそのまま使っている(`enterGroup`/`exitGroup` がストアの `nodes`/`edges` を丸ごと差し替えるだけなので、既存アクションからは「今どの階層を編集しているか」を区別できない)。多段ネスト(グループの中の別グループ)も自然に成立する。`editor/NodePalette.tsx`/`editor/ContextMenu.tsx` は `scopeStack.length > 0`(=グループの中に入っている)の場合だけ「Group I/O」カテゴリを一覧に含める — トップレベルに置いても意味を持たないため。
  - **落とし穴**: グループの中に入っている間、`state/graphStore.ts` の `nodes`/`edges` は「今開いている階層」の内部ノードだけになるため、これを直接見るコードは他ガーメントの消失やボディスケールのリセットを引き起こしうる(実際に設計時に見つかった欠陥)。トップレベル視点の完全なグラフが必要な箇所は代わりに `rootEvaluatedResults`(`composeRootGraph()` 経由)を見る必要がある — 詳細・対象箇所・回避策は `src/state/CLAUDE.md` の「グループの中に入る」節を参照。
  - **`removeGroupIOSocket(nodeId, socketId)`**(`state/graphStore.ts`): `groupInput`/`groupOutput` ノードのソケットを1つ削除する専用アクション。単なる `updateNodeData()` と違い、(1) 同じハンドルidを参照する現在階層の内部エッジ、(2) グループの中に入っている場合、そのグループノード自身は現在の `nodes` には無く直近の `scopeStack` フレームに退避されているため、そのフレームの `edges`(親ノードから見た外部接続)の中で同じハンドルidに繋がっている外部エッジ、の両方も同時に削除する。外部エッジが残っている場合は削除前に確認ダイアログを出す(孤立エッジ — ハンドルが消えて繋がって見えないエッジ — を防ぐ、上記「グループの中に入る」の落とし穴と同種の対策)。`exitGroup()` 時の書き戻し(`{...n.data, nodes, edges}`)は `nodes`/`edges` だけ上書きするため、内部の `groupInput`/`groupOutput` ノードの `data.sockets` の変更はそのまま親ノードへ引き継がれる。
- `evaluate()` は、外部から渡された入力値(`inputs: Record<string, SocketValue>`)を埋め込みサブグラフ内の `groupInput` ノードの `data.injected` へ評価のたびに一時的に注入してから(`data` として永続化されるわけではない、この1回の `evaluateGraph()` 呼び出し限りのパッチ)、`evaluateGraph()` を**再帰的に**呼ぶだけ。未接続の外部ソケットは `inputs` に現れないため、`groupInput.evaluate()` 側で各ソケット自身の `default` にフォールバックする。`groupInput` ノード自体が無い場合はこの注入先が無いため、`inputs` に何を渡しても単に無視される(そもそも `def.inputs` が空なので外部から接続しようがない)。`nodes/evaluateGraph.ts` 自体はほぼ無改修(未接続ソケットの解決を `resolveNodeSockets()` 経由にした1点のみ変更)。
- **注入できる型に制限は無い**(`groupInput` ノードの出力ソケットとして SocketValue をそのまま流し込むだけなので、geometry/material も注入できる)。ただし実際に使う既存14種は、他ガーメントと共有される値(`bodyBuild`、取り付けアンカー座標の `anchorY`、bodyGroup と pants/shoes/socks が共有する `legSpacing`、bodyGroup と gloves が共有する `shoulderSpacing`(gloves では `armSpacing`))だけを外部入力にしており、ガーメント固有の生パラメータ・Color は外部入力にせず埋め込みサブグラフ内部の `numberInput`/`colorInput`/`enumInput` ノードとして保持している(ルート [`CLAUDE.md`](../../CLAUDE.md) の「Body(3Dモデル本体)も他14種のガーメントと同じ `<name>Group` ノードで組み立てられる」節参照)。**Height/Shoulder のスケールはどのガーメントグループにも直接配線されていない** — `bodyDimensionsGroup` 内部の `numberInput`(`heightScaleIn`/`shoulderScaleIn`)としてのみ存在し、この階層より外には現れない。アンカー座標の計算は `bodyDimensions`/`bodyLayout` という2つのトップレベル共有ノードが担うため、各グループが直接必要とするのは計算済みの `anchorY`(1個の数値)だけになる。`bodyBuild` だけは、ガーメント自身の「体に触れる半径」をスケールする10種(belt/dress/gloves/jacket/pants/scarf/shoes/socks/skirt/top)について、`bodyDimensions` への配線とは別に直接の外部ソケットとしても受け取っている(下記参照) — こちらは `bodyDimensions` を経由しない、ガーメント自身の半径スケーリング専用の配線。
- **値が複数グループで共有される場合は、その値をどちらかのグループの内部に閉じ込めて `groupOutput` で覗き穴を開けるのではなく、`bodyBuild`/`bodyDimensions` と同じく `src/state/initialGraph.ts` 側のトップレベルの共有ノードへ引き上げ、各グループへ普通の外部ソケットとしてファンアウトすること**。`bodyDimensions` が計算する脚の間隔 `legSpacing`(bodyGroup と pants/shoes/socks が共有する)・肩幅 `shoulderSpacing`(bodyGroup と gloves が共有する)がこの例。一方、同じグループの中だけで使い回す値(top の Torso Radius と Color を Top 本体と袖が共有する場合など)は共有ノードにせず、グループ内部の1つのノードから内部の複数の生成ノードへ配線すればよい(`topGroupNode.ts` 参照)。
- **`sceneOutput` はグループの埋め込みサブグラフの中に置く**(既存14種すべてがこの形)。**1つのグループの中に `sceneOutput` は何個置いてもよい**。中に入って `sceneOutput` ノードを `garmentPlacement`/`toonMaterial` などから配線すると、`groupNodeFactory.ts` の `evaluate()` が内部の `findResolvedSceneOutputs(internalNodes, internalResults)` を呼び、`internalNodes` を先頭から順に見て、見つかった解決済みの geometry+material の組をすべて集める。1つのノードから見つかる形は2通り: (1) `type === 'sceneOutput'` のノード自身(`groupOutput` を探すのと同じ、型名によるパターン)— その評価結果が geometry+material の両方を持っていれば採用する(1つのグループの中に複数あってもよいので、1つ見つけても探索は続ける)。(2) それ以外の任意のノード(典型的にはネストした別のグループノードインスタンス)— その評価結果が既に `sceneOutputGeometry<N>`/`sceneOutputMaterial<N>`(そのノードがさらに1つ内側から転送してきた予約キー、1組とは限らない)を持っていれば、そのすべてを採用する。集まった組を先頭から 0,1,2,... と振り直し、`sceneOutputGeometry<N>`/`sceneOutputMaterial<N>` という予約キーでグループ自身の外部出力(`groupOutput` があればその転送分と同じ Record、無ければ空オブジェクトへ追加)へ加える。このキーはグループの静的な `outputs`(`groupOutput` があればその `data.sockets` から導出される、パレット上で見える入出力ソケット)には含まれず、他ノードへ配線するための一般的なソケットではない — `Garments.tsx` だけが読む専用チャンネルで、`numberDisplay` が `outputs: []` としながら `evaluate()` で `value` キーを返すのと同じパターン。`Garments.tsx` はグループの型を問わずこのキーが1つでもあれば、見つかった数だけ独立した `ToonMesh` として描画する(上記「出力カテゴリのノード」節、`src/scene/CLAUDE.md` 参照)。この内部配線を消してしまう(または `sceneOutput` ノード自体・その入力を削除してしまう)と、そのメッシュは単に描画されなくなる(フォールバックを持つ中継ノードは無い)。`anchorY`/`offsetY` はこの経路には一切乗らない — `garmentPlacement` が内部で消費してジオメトリの頂点座標へ焼き込むため、`input.anchorY`/`offsetYIn → garmentPlacement` の配線を消すと(`garmentPlacement` 自身もフォールバック `anchorY: 0`/`offsetY: 0` を持つので)取り付け位置だけが原点付近のデフォルトに戻り、描画自体は消えない。**多段ネスト(グループの中の別グループ)にも対応している** — 各階層の `evaluate()` が同じ `findResolvedSceneOutputs()` を呼ぶだけなので、孫グループの内部 `sceneOutput`(複数でも)は子グループを経由して祖父グループまで、何階層でも自動的に転送・再インデックスされる(特別な再帰処理は無く、`groupNodeFactory.test.ts` の「多段ネスト」ケースで検証している)。インデックスの割り当て順は `internalNodes` の並び順で決まり、優先順位を隠し持たない。
- 新しいガーメント種をこのパターンで追加する手順は `add-garment-type` スキルを参照。

## 汎用ノード一覧(特定のガーメント/パーツに紐付かないノード)

新しいノードを書く前に、近い処理をする汎用ノードが既に無いか確認すること — 同じ処理を専用ノードとして重複実装し、後から統合し直す手戻りがこのプロジェクトで何度も発生している(例: pants/shoes/gloves/socks がそれぞれ独立に左右対称ペア化ロジックを持っていたのを後から `mirrorPair` へ統一)。

- **数値演算**: `numberAdd`(A+B)/`numberSubtract`(A-B)/`numberMultiply`(A×factor)/`numberMax`(`Math.max(a,b)`)/`numberNegate`(`-value`、符号反転専用の単項演算ノード)/`numberHalf`(`value × 0.5`、半分にする専用の単項演算ノード)。`numberDisplay` は評価値をノードカード上で確認するためだけの終端ノード(`outputs: []` としながら `value` を返す)。
- **geometry の変換**: `translateX`/`translateY`/`translateZ`(各軸方向へ平行移動)、`scaleZ`(Z方向のみ非一様スケール)、`mergeGeometry`(入力ソケット `geometries` に繋いだすべての geometry を結合する。複数接続できるソケットなので、パーツの増減は配線を足す/切るだけ。1つだけならそのまま出力する)、`mirrorPair`(1つの geometry を ±offset の左右対称ペアへまとめるグループノード、内部は `translateX`×2+`mergeGeometry`)。
- **points の生成/変換**(Lathe用、`points` は `easedLatheProfile`/`latheGenerator` の間を流れる `THREE.Vector2[]` の専用ソケット型): `easedLatheProfile`(半径を smoothstep でイージングしながら結ぶプロファイル点列を生成)→`latheGenerator`(points から `THREE.LatheGeometry` を生成)。`translatePointsY`(points をY方向へ平行移動)/`slicePoints`(points の末尾から指定個数を取り除く)/`concatPoints`(2つの points を連結) — belt のようにプロファイルを2回呼んで連結する場合に使う。
- **プリミティブ生成**: `capsuleGenerator`/`sphereGenerator`/`cylinderGenerator`(上下の半径を独立指定できるテーパー円柱)/`torusGenerator`/`boxGenerator` — いずれも `geometry/primitives.ts` の `build*Geometry()` を THREE.js 標準プリミティブへ薄くラップしただけ。`alignedBoxGenerator` — `geometry/alignedBox.ts` の `buildAlignedBox()`(2点間を結ぶよう回転+平行移動した `THREE.BoxGeometry` を作る、剛体変換のみなので巻き順がそのまま保たれる)を薄くラップしたもの。始点・終点をそれぞれ X/Y/Z の3ソケットに分解している(bag のストラップ、glasses のブリッジ/テンプルが使う)。
- **取り付け位置**: `garmentPlacement` — `anchorY`+`offsetY` を geometry の頂点へ焼き込むグループノード(詳細は上記「配置情報の生成」参照)。
- **入力/出力**: `numberInput`/`colorInput`/`enumInput`(リテラル値の入力)、`toonMaterial`(color から `MeshToonMaterial` を生成)、`sceneOutput`(描画専用の終端ノード、上記「出力カテゴリのノード」参照)。
